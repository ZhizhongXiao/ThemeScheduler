# 通知、自检与修复契约

版本：`0.1.3`
状态：通知交互、自检修复和错误健康入口均已完成验收

## 1. 范围

通知与健康层只增强异常可见性和自助恢复，不改变主题事务、时间判断、暂停语义、任务结构或安装边界。

本阶段包含：

- 本地 Windows 应用通知；
- AppUserModelID、进程身份和开始菜单快捷方式关联；
- 配置、状态、颜色记录、程序文件、权限、任务、Windows 访问和通知能力自检；
- 显式、可重复、可验证的修复操作；
- 通知失败后的结构化日志后备。

本阶段不包含：

- 托盘常驻、后台通知服务、联网推送或遥测；
- 文本输入、远程图片、任意命令或不受验证的通知激活；错误通知仅允许固定无参数健康入口；
- 静默修复不可信配置、状态、颜色记录或程序文件；
- 自动安装 Windows App SDK、.NET Runtime 或其他系统运行库。

## 2. 应用身份

候选稳定身份为：

```text
AppUserModelID = ThemeScheduler.ThemeScheduler
```

D-09 冻结后该值视为安装契约，不能在普通升级中变化。

要求：

1. 正式进程在调用通知 API前设置同一显式 AppUserModelID；
2. 开始菜单快捷方式必须包含 `System.AppUserModel.ID`；
3. 可选桌面快捷方式存在时使用相同身份；
4. Setup、同版本重装、升级和系统集成修复都要读回该属性；
5. 快捷方式同时携带固定占位 Toast CLSID，使通知保留在通知中心；
6. 当前用户协议登记只允许 `themescheduler-action:`，命令固定指向已安装主 EXE 的通知动作入口；
7. 卸载删除产品快捷方式和协议登记，不遗留通知激活入口。

快捷方式写入仍属于阶段 8 的系统集成事务：修改前按原始字节捕获，失败按字节恢复。身份漂移不得只靠 WSH 可见字段判断。

## 3. 通知策略

### 3.1 自动切换预通知

每一次可执行的固定或延迟切换都必须有一对触发点：

```text
scheduledAt - 5 minutes → 发送预通知并建立一次性动作 nonce
scheduledAt             → 执行本次决定；SKIPPED 时保留 occurrence 抑制标记
nextFixedAt             → 清理已 supersede 的 SKIPPED 标记并恢复下一周期
```

预通知显示：

- `跳过本次`：本次目标不应用；`SKIPPED` 标记保留到 `nextFixedAt`，同一 occurrence
  的后续 auto 仍跳过，不得因重复任务启动或关闭状态通知而重新应用目标；
- `延迟 30 分钟`：本次执行时间改为 `scheduledAt+30min`，并建立新的 `+25min` 预通知与 `+30min` 执行触发；
- `确认`：保持原 `scheduledAt`，不立即切换；
- 无操作：与确认相同，按原计划执行。

延迟后的执行点必须重新经历完整的五分钟决策窗口。例如原定 `T` 的切换被延迟后，建立 `T+25min` 的新预通知触发和 `T+30min` 的新执行触发；到 `T+25min` 才生成新的 nonce 并再次显示同样三个按钮。再次延迟则建立 `T+55min`/`T+60min`，不得沿用上一轮 nonce 或省略新预通知。延迟不得越过下一固定昼夜边界；若下一次延迟会跨界，界面不提供延迟动作并把未完成旧目标在下一固定边界前收束。一次性 nonce 只绑定一个计划时间、一个目标时段和一次动作，过期或重复请求必须拒绝。

设备在预通知时不可用、直到执行时间后才恢复时，按错过边界规则直接校准当前目标，不补发已经失去决策窗口的预通知。

### 3.2 保持静默

以下自动结果不发送成功通知：

- 当前可信配置已匹配目标；
- 另一实例正在运行；
- 计划任务在暂停状态下触发。

实际完成并验证主题切换后等待 5 秒，再发送成功通知。等待与投递位于核心事务之后；进程在这 5 秒内退出只影响成功提示，不影响已提交的主题结果。
预通知使用固定的本地通知 tag/group；执行点消费本次决定时先从通知历史撤回预通知，再发送成功或错误提示。用户无操作时也不得在切换后留下按钮已经失效的旧预告；延后后的新预告必须替换上一张预告。

### 3.3 错误通知

仅当 `notifications.errors=true` 时提示：

- 配置、状态或颜色记录不可信；
- Windows 访问能力不可用；
- 主题应用失败、回滚失败或结果部分可信；
- 状态提交失败或中断恢复需要用户处理；
- 运行清理或结构化日志写入失败。

同一错误事件和错误码默认 6 小时内只弹出一次；新的部分事务或不同错误码不被错误去重。去重状态属于 `runtime/` 缓存，不是用户配置，卸载时始终删除。

错误通知正文只允许固定 `themescheduler-action://health/` 激活。GUI 未运行时打开维护区；GUI 已运行时通过当前会话命名事件恢复并聚焦原窗口，不创建第二个窗口。随后自动运行一次只读健康检查并定位报告。该 URI 不接受查询参数、片段、路径扩展、修复动作或任意命令；点击不会修改主题、任务、配置或状态。成功通知不设置点击激活，预通知仍只包含三个受 nonce 保护的切换按钮。

### 3.4 状态通知

仅当 `notifications.statusChanges=true` 时提示：

- 用户主动暂停或恢复；
- 显式修复的成功、无变化、部分成功或失败。
- 固定或延迟计划的预通知与实际切换成功。

关闭 `notifications.statusChanges` 后不发送预通知、不提供跳过/延迟能力，也不发送成功通知；自动切换仍按固定边界执行。保存普通配置不显示状态通知。

### 3.5 失败后备

通知在核心用例返回后执行：

```text
核心事务完成并确定退出码
→ 根据配置和结果决定是否通知
→ 尝试本地通知
→ 失败时追加 notification.delivery-failed 结构化日志
→ 保持原核心结果和退出码
```

通知后端故障不得回滚主题、状态、任务或配置。日志后备也失败时，计划任务仍返回原核心退出码；GUI 或显式诊断入口可以附加警告，但不能把已经验证成功的核心操作改写为失败。

通知内容固定标题 `ThemeScheduler`，正文不超过 240 字符，不包含完整文件路径、注册表数据、主题内容或堆栈。详细诊断只进入本地日志。

## 4. 健康报告契约

`themescheduler.health-report` v1 的单项状态为：

| 状态 | 含义 | 行为 |
| --- | --- | --- |
| `healthy` | 已验证符合预期 | 无操作 |
| `warning` | 功能仍可用或当前选择导致能力受限 | 给出说明，不提供自动修复 |
| `repairable` | 产品拥有明确、幂等且可验证的修复动作 | 仅在用户确认后执行命名修复 |
| `action-required` | 数据不可信、程序损坏或外部策略阻止 | 停止相关写入，指导用户处理或重装 |

总体状态取最严重单项：`action-required > repairable > warning > healthy`。检查 ID 必须稳定且唯一；只有 `repairable` 可以返回 `repairAction`。

## 5. 检查矩阵

| 检查 ID | 内容 | 典型异常 | 分类 |
| --- | --- | --- | --- |
| `configuration.config` | 严格加载 `config.json` | 缺失、损坏、未知版本 | `action-required` |
| `data.state` | 严格加载状态并检查未完成事务 | 不可信或歧义 Windows 状态 | `action-required` |
| `data.profile.day/night` | 严格加载两份语义颜色 | 缺失或哈希/字段错误 | `action-required` |
| `files.payload` | 安装记录、清单和活动载荷 | 文件损坏或混装 | `action-required`，重新运行 Setup |
| `permissions.data-write` | 在固定 `runtime/health/` 建立、刷盘并删除探针 | 无法写入或无法清理 | `action-required` |
| `permissions.log-write` | 验证结构化日志可追加 | 日志不可写 | `action-required` |
| `task.definition` | 读取并比较单任务 v2 固定触发器及可信延后触发对 | 缺失、定义漂移或延后状态不一致 | `repairable: task.repair` |
| `windows.theme-access` | 只读探测主题、应用模式与桥接能力 | 权限、策略或组件不可用 | `action-required` |
| `notification.identity` | 进程/开始菜单快捷方式 AUMID 一致 | 缺失或漂移 | `repairable: notification.identity-repair` |
| `notification.platform` | 桥接、系统设置和能力探测 | 用户关闭通知 | `warning`；桥接损坏为 `action-required` |

普通健康检查不得弹通知、修改任务、主题、配置或状态。权限深检只允许在固定用户数据根写入一次性探针并立即清理；若清理失败，报告确切残留。

## 6. 修复权限

健康检查本身不自动修复。

错误通知触发的健康检查与用户点击“运行完整健康检查”使用同一只读用例。前端以中文呈现四级状态并把报告滚动到可见位置；即使结果为 `repairable`，也只能由用户随后点击对应修复按钮并再次确认。

阶段 9 首版只提供两项受控修复：

1. `task.repair`：复用配置、可信一次性覆盖状态与任务契约，完整替换并读回单任务 v2 定义；重复执行幂等；
2. `notification.identity-repair`：只重建产品拥有的开始菜单快捷方式、已经存在的桌面快捷方式和 `themescheduler-action` 协议；不擅自创建桌面快捷方式，使用原始字节/注册表树备份和读回验证。

不可信配置、状态、颜色、安装备份、程序载荷或 Windows 访问问题均不得猜测修复。程序文件损坏继续通过 Setup 事务式重装处理。
