# ThemeScheduler 1.0.0 发布路线

状态：已完成
建立日期：2026-09-13

## 1. 当前起点

- `0.1.3` 是进入本路线时的正式发布基线；
- `0.1.4` 的权威当前外观读取修复已完成定向实机验收；
- `0.1.5` 已实现昼夜分别配置 Windows 模式、应用模式、强调色及两个强调色显示
  位置，并取消自动边界学习；
- `0.1.5 RC2` 已通过 577 项 release 测试、Coverage 棘轮、连续双构建、PE/payload
  校验、Defender 扫描和完整外观人工实机矩阵；
- 原 67 个 `test_*.py` 已按 `unit/integration/release` 迁移，当前为 70 个测试模块；
  发现规则显式限定三个测试包，全源码采用 Pyright basic，十二个高价值模块进入
  strict；任务计划桥已经完成 20 样本性能基线和“不批量化”的决策；
- 动态主题兼容后的最新 0.1.5 候选通过 603 项 release 测试、Coverage 棘轮和真实
  `spotlight.theme` 应用，产品完整健康检查为 11/11 正常。

`0.1.5 RC2` 是 1.0 功能基线的资格候选，不是可改名的 `1.0.0` 二进制。后续文档、
测试结构和质量配置会改变源码身份，因此最终 1.0 必须重新构建和验收。

## 2. 发布原则

1. 从本路线建立起冻结新功能；只接受阻断 1.0 的缺陷、测试和可维护性改进。
2. 每一阶段先保持上一阶段门禁通过，再改变下一项；不把测试迁移、类型收紧和性能
   重构混成一次不可定位的大修改。
3. 不为覆盖率或 strict 数量删除防御性校验、回滚路径或 Windows 失败分支。
4. 性能优化必须由测量触发；没有明确收益时保留现有、较易回滚的桥接实现。
5. 人工 Windows 写入必须单独授权，执行后恢复配置、任务和外观基线。

## 3. 阶段 A：确认 0.1.5 功能基线（已完成）

使用已经通过自动门禁的 `0.1.5 RC2-A`，最后执行一次完整外观实机矩阵：

- 安装或升级后版本、GUI、任务入口正常；
- 昼夜分别设置不同的 Windows 模式、应用模式、强调色和两个显示位置；
- “导入当前 Windows 外观”只更新所选时段草稿，且读取五项实时外观；
- 普通保存不立即改变 Windows；“保存并应用当前时段”应用完整目标；
- 一次真实计划边界应用另一时段的完整目标；
- 开始菜单/任务栏与标题栏/窗口边框的两个开关分别通过肉眼确认；
- 恢复安装前外观后，两种模式、颜色和两个开关与恢复点一致；
- 验收结束恢复原配置、任务和 Windows 外观。

自动故障注入继续承担复合事务回滚证明，不为制造真实系统故障而破坏开发机。

退出条件：上述项目全部通过并形成简短实机记录。若失败，先修复 0.1.5 功能基线，
重新执行受影响门禁和候选构建，不进入阶段 B。

完成记录：2026-09-13 使用 RC2-A 从 0.1.4 升级，验证完整外观导入、仅保存、手动
应用当前时段和真实任务边界；昼夜两组 Windows 模式、应用模式、强调色及两个显示
位置均按计划读回。结束后 7/7 项受保护数据状态、原任务和验收前 Windows 外观均
精确恢复，0.1.5 保持安装。阶段 B 可以开始。

## 4. 阶段 B：整理测试目录与发现规则（已完成）

在不改变产品行为的前提下，将平铺测试按职责迁移为：

```text
tests/
  unit/          # 纯模型、算法、解析和服务单元测试
  integration/   # 跨组件、前后端契约和 Windows 适配器模拟测试
  release/       # 打包、清单、PE、产物与发布门禁测试
  fixtures/      # 领域专用 Fake 和共享构造器
  ui/            # Node/DOM 侧测试资源
```

同步更新 `tools/test.py`、分组映射、`pyproject.toml` 的逐文件规则、源码/发布清单契约
和所有读取测试源码路径的断言。迁移前后必须满足：

- `quick`、`affected`、`integration`、`coverage`、`release` 均能发现预期集合；
- 不重复运行同一测试，也不因目录变化漏测；
- 迁移前已有测试数量不下降，测试标识的语义保持可追踪；
- Coverage 使用同一源码范围，逐模块棘轮不下降。

退出条件：目录结构、发现规则和文档一致，完整 release 门禁通过。

完成记录：迁移前冻结 67 个文件、577 项测试及 15 个 quick/affected 分组的测试
ID；迁移后为 unit 24、integration 32、release 11，根目录无测试模块。运行器显式
遍历三个测试包，原 577 项在所有模式中无缺失、无重复，新增 2 项目录/发现契约。
integration、coverage、Coverage 棘轮和 release 的最终结果见本阶段提交。

## 5. 阶段 C：补高风险 Windows 分支（已完成）

优先补充能够阻止真实回归的模拟和契约测试：

1. GUI 启动：WebView2 缺失/初始化失败、已有实例聚焦、安装态入口和窗口退出；
2. Explorer 恢复：启动失败、超时、错误会话、恢复进程失败和不误杀其他会话；
3. Windows 组合适配器：注册表值缺失、错误类型、部分写入、主题成功但显示位置验证
   失败、回滚二次失败及中断恢复；
4. Task Scheduler：PowerShell 超时、非零退出、无效 JSON、访问拒绝和完整 XML 回滚。

真实 Windows API 难以稳定自动化的场景使用 Fake/Mock 验证输入、调用顺序、隐藏窗口
标志、错误分类和回滚结果；不以追求总覆盖率数字替代风险选择。

退出条件：新增测试能在移除对应保护时失败，integration、coverage 和 release 均通过。

完成记录：新增 12 项风险测试，直接覆盖 WebView2 缺失、窗口创建/初始化失败与激活
清理，Explorer 超时/启动失败/错误会话及 PID 作用域，外观注册表部分写入和二次回滚
失败，以及任务桥访问拒绝 HRESULT。既有测试继续覆盖自动事务各中断阶段、任务桥
无效 JSON/超时和完整 XML 恢复。测试发现了“显示位置第二次写入失败时仍重复应用
未改变的主题”缺陷；回滚现先验证当前视觉状态，已经等于原目标时只恢复注册表快照。

## 6. 阶段 D：扩大 Pyright strict 棘轮（已完成）

保持完整 `src/theme_scheduler` 的 basic 零诊断，以单文件为单位处理下一批边界：

1. `configuration_service.py`；
2. `maintenance_service.py`；
3. `automation/backend.py`；
4. `scheduled_auto.py`；
5. `accent_service.py`。

每次只把已经零 strict 诊断的文件加入 `pyproject.toml`。允许用具名 Protocol、
TypedDict、窄化助手或更准确的返回类型修复问题；不得批量 `Any`、`cast`、
`# type: ignore` 或降低规则伪造通过。候选顺序可按实际依赖微调，但必须在提交说明中
记录原因。

退出条件：至少完成上述高风险边界的可行子集；无法合理收紧的文件记录具体诊断和
阻塞原因，不因追求全量 strict 阻止 1.0。

执行结果：五个候选全部进入 strict，全源码仍为零诊断。`maintenance_service.py` 与
`scheduled_auto.py` 无需源码调整；另外三个模块以具名运行时窄化助手和显式容器类型
消除 Unknown/不必要类型判断，同时保留面向反序列化、插件后端和 Python 调用方的
防御性校验。未使用批量 `Any`、`cast`、忽略注释或降低规则。

## 7. 阶段 E：任务桥性能测量与决策（已完成）

先建立只读基准，不直接改变桥协议：

- 分别测量 PowerShell 冷启动、单次任务读取、连续读取和完整健康检查；
- 记录预热轮次、样本数、Windows/PowerShell 版本、p50、p95 和最大值；
- 将进程启动成本与脚本/COM 操作成本分开；
- 基准默认使用现有产品任务的只读查询，不创建、修改或删除任务。

只有当完整健康检查的用户可见 p50 超过 1 秒，且两个以上任务桥进程启动占总耗时
至少 50% 时，才为“批量只读桥接”建立独立实施项。实施时必须保留单操作接口、
结构化错误、超时、隐藏窗口和等价测试；写操作与回滚不在本轮合并。若未达到阈值，
记录“维持现状”即视为阶段完成。

退出条件：保存可复跑命令、环境和统计结果，并形成“实施”或“不实施”的明确决策。

执行结果：Windows 11 build 26200、Windows PowerShell 5.1、Python 3.12.10 上以 2 次
预热和 20 个样本运行 `tools/task_bridge_benchmark.py`。主题兼容源码完成后重新绑定的
报告中，PowerShell 启动、单次任务读取和三次连续读取的 p50 分别约为 120、315 和
每次 328 ms；完整健康检查 p50 约 2578 ms。健康检查确实启动 2 次任务桥，但任务桥
耗时占比 p50 仅约 23.0%，且 20 个样本的最大占比为 24.8%，仍低于 50% 门槛，因此
决定保留单操作桥，不在 1.0
前增加批量只读协议。机器报告保存在忽略态
`artifacts/quality/task-bridge-benchmark.json`，命令与判断逻辑由单元测试固定。

重新采集时的活动主题为 Windows 预设 `spotlight.theme`；20 个完整健康检查样本全部
为 `healthy`。报告绑定 121 个实际输入文件，身份为
`9b9dea099dc3fd340da64f855cc4c561801d20fe5e918f9239c6b0caa0900c6e`。无
`[VisualStyles]` 的真实自定义主题采用下述组合证据收口，不要求不可稳定复现的第二次
现场生成。

## 8. 阶段 F：生成并发布 1.0.0

完成 A–E 后才执行版本升级：

进入条件增补：2026-09-14 在 Windows 11 build 26200 观察到系统生成的 458 字节
`Custom.theme` 只有 `[Theme.A]`/`[Theme.W]`，没有 `[VisualStyles]`；切换预设主题后
又观察到标准 `[VisualStyles]` 与缺失 `ThemeId` 的组合。双格式兼容源码、去隐私夹具、
首次安装恢复点、健康探针和事务回滚自动测试已经完成；0.1.5 兼容候选又在真实
`spotlight.theme` 上完成应用。既有的 DWM 滞后问题也完成回归确认：Windows 设置改色
后公共颜色 API 返回 `#BFBFBF`、旧 DWM 值仍为 `#744DA9`，GUI 正确导入前者。以上
组合证据解除阶段 F 的主题格式阻塞；
不以忽略健康错误、人为改写 `CurrentTheme` 或反复盲试替代修复。

1. 将包版本、`__version__`、三份 EXE 版本资源、安装器预览、清单和用户文档统一为
   `1.0.0`；
2. 更新锁文件并运行 integration、coverage、Coverage 棘轮和 release；
3. 使用同一源码身份连续构建两次，比较 Setup、主程序、Uninstall 和 payload
   manifest 的 SHA-256；
4. 复核三个 EXE 均为 PE32+ x64、Windows GUI、版本 `1.0.0`；
5. 使用 Defender 扫描最终三个 EXE，并复验全部 payload 与发布哈希；
6. 用最终 Setup 完成一次精简安装/升级、计划应用、同版本修复和控制面板卸载；
7. 核对退出自清理和零残留，冻结到 `artifacts/releases/1.0.0`；
8. 最后更新正式版本状态，提交 Git/GitHub 并创建非预发布的 `v1.0.0` Release。

完成记录：`1.0.0 RC6` 通过 607 项 release 门禁、Coverage 棘轮、连续双构建、
PE/payload 校验及 Defender；从 0.1.5 升级、完整健康检查和真实桌面用户环境下的
安装前外观恢复、控制面板卸载及零残留核对通过。阶段 F 已满足冻结条件。

任何第 1–5 步之后的源码或发布文档修改都会改变源码身份，必须重新运行 release 和
双构建。不得把 0.1.5 EXE 仅改文件名或 Git 标签后当作 1.0.0。

## 9. 1.0.0 完成定义

只有同时满足以下条件，才能称为正式 1.0：

- 0.1.5 完整外观实机矩阵通过；
- 测试结构和发现规则完成迁移且无漏测；
- 高风险 Windows 分支获得最小充分安全网；
- strict 棘轮按风险扩大且全源码 basic 仍为零诊断；
- 任务桥形成有数据支持的实施/不实施结论；
- 真实标准主题应用与公共颜色读取通过；真实缺节格式观察和脱敏夹具事务/回滚通过；
- 最终 1.0.0 源码通过门禁、双构建、Defender 和最终生命周期验收；
- 正式发布目录、Git 提交、标签、GitHub Release 和用户文档版本一致。
