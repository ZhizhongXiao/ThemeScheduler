# ThemeScheduler 0.1.3 开发计划

状态：代码与自动门禁完成；RC1 Windows 实机写入验收通过。

## 产品变更

设置页使用两个清楚的提交动作：

1. **保存计划**：保存配置、昼夜颜色并更新任务，不修改 Windows 外观。
2. **保存并应用当前时段**：先保存计划，再按真实当前时间应用已提交的昼间或
   夜间外观。

概览页不增加独立立即同步按钮。暂停状态不阻止明确的手动应用，也不会被手动
应用解除。首次设置继续在第一次成功保存后启用自动切换。

## 代码收口

- 删除工作台 `validate_config`、`save_config` 旧接口及专属契约测试；
- 用正式外观模型承接生产依赖后，删除阶段 1 `theme.py`、`cli/theme.py`
  及专属原型测试；
- 用正式强调色模型承接生产依赖后，删除 `accent.py` 的旧诊断原型与专属测试；
- 从自动运行器移除 `force_apply`，建立独立手动外观服务。

## 维护与调试信息架构

- 维护页承载恢复默认设置、检查/修复任务、按健康结果建议修复通知身份、打开
  产品目录及启动卸载器；
- 调试页只承载健康检查、诊断摘要、复制摘要、检查详情和近期日志，不直接执行
  修复。

## 已完成的交互设计

- **UI-013-01 操作确认窗口**：保存并应用、恢复安装前外观和修复动作统一使用
  WebView 内上下、左右居中的模态确认窗；支持 Esc 取消、取消优先焦点及关闭后
  焦点归还，不再依赖位置不可控的 Chromium 原生确认框。
- **UI-013-02 操作结果提示**：建立操作级中文映射；保存、控制与修复结果使用
  中央短提示，失败适当延长，低权重且已有页面反馈的操作不再弹出。表盘切换继续
  使用同一中央短提示。两类交互已在安全预览及 RC2 安装态完成目视验收。

组合动作使用稳定的 `save-workspace-and-apply` envelope，并分别携带
`planSaved`、`save`、`application` 和 `targetProfile`；前端呈现不得
改变保存与外观事务的真实结果。

## 实施顺序

1. 冻结控制契约和测试矩阵；
2. 实现独立手动外观服务及组合保存结果；
3. 接入设置页双按钮；
4. 删除旧工作台接口与 `force_apply`；
5. 迁移并删除主题/强调色原型；
6. 重排维护与调试入口；
7. 完成自动门禁和 Windows 实机验收。

前六项及自动门禁已经完成。RC1 已在 Windows 实机验证“保存计划”只更新配置与
任务而不改变外观，以及“保存并应用当前时段”按真实时间选择昼间配置并应用；
验收后六项用户数据、任务和 Windows 外观均精确恢复。暂停状态保持、保存失败
阻断应用以及应用失败保留计划由自动化测试覆盖，不以故障注入扩大本轮实机写入
范围。UI-013-01 与 UI-013-02 已在 RC1 后续源码中实现并通过安全预览目视验收；
它们需要进入下一候选构建后，再随最终安装态冒烟一并冻结。
