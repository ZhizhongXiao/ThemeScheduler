# ThemeScheduler 设计文档

版本：设计基线 v0.2  
适用范围：Windows 11 x64、当前用户安装、单用户个性化设置

## 1. 文档目的

本文定义 ThemeScheduler 第一版的业务规则、数据模型、自动切换算法、GUI 行为以及安装维护流程。系统边界和组件职责见 [ARCHITECTURE.md](ARCHITECTURE.md)，当前维护事项见 [BACKLOG.md](BACKLOG.md)，目录、事务、登记和清理细节见 [INSTALLATION.md](INSTALLATION.md)。

## 2. 功能范围

第一版需要实现：

1. 每天按固定时间切换昼间和夜间配置。
2. 分别保存两个时段的应用模式和强调色；不修改“选择模式”和“默认 Windows 模式”。
3. 允许用户在 Windows 设置中临时修改主题或颜色，并保持到下一固定计划时点。
4. 设备睡眠或关机期间不主动唤醒，重新可用后按当前时间校准。
5. 支持暂停、恢复和任务修复；不提供偏离计划边界的手动立即套用外观操作。
6. 通过 GUI 安装、配置、升级、卸载并选择是否恢复 ThemeScheduler 接管前的应用模式和强调色。
7. 保存必要状态和轮换日志，异常时提供通知或日志后备。
8. 发布程序不依赖目标设备预装 Python。

第一版不实现常驻托盘、注册表实时监听、三个以上时段、日出日落、任意 RGB 调色板生成、第三方应用强制主题、云同步和多用户管理。

## 3. 术语与时段计算

- **昼间边界**：进入昼间配置的固定时间。
- **夜间边界**：进入夜间配置的固定时间。
- **目标时段**：根据当前本地时间计算出的 `day` 或 `night`。
- **活动时段**：状态中记录的上一次成功归属，用于判断当前强调色应保存给哪个时段。
- **强调色配置**：从 Windows 当前活动主题学习的最小语义颜色，包括自动取色状态和原始 `ColorizationColor`；经典调色板注册表值只用于诊断。
- **主题事务备份**：一次强调色应用前保存的完整活动 `.theme` 文件及其清单，只用于当次回滚，不作为昼夜长期配置。

默认时间：

```text
dayStart   = 06:15
nightStart = 23:45
```

工作日与周末使用同一计划。时间区间按本地墙上时间构成圆环。当 `dayStart < nightStart` 时：

```text
dayStart ≤ 当前本地时间 < nightStart  → day
其他时间                                → night
```

当 `dayStart > nightStart` 时，`当前时间 ≥ dayStart` 或 `当前时间 < nightStart` 为昼间，其余为夜间。配置校验必须拒绝相同的两个边界时间。第一版只支持两个固定边界形成的一个昼间区间和一个夜间区间，不引入星期规则。时钟必须返回带 UTC 偏移的当前本地时间；夏令时、手动校时、休眠或关机后只按启动时的本地墙上时间判断，不补算历史目标。

## 4. 默认主题配置

### 4.1 不变量

程序不得修改 Windows 设置中的“选择模式”和“默认 Windows 模式”。用户当前采用“自定义 + 默认 Windows 深色”时，该组合在昼夜切换前后保持不变；即使用户以后手动调整这两项，程序也不负责纠正或恢复。

### 4.2 昼间

```text
应用模式：浅色
```

开始菜单、任务栏等系统界面保持用户现状（当前为深色），Edge 等支持“跟随系统”的应用使用浅色。

### 4.3 夜间

```text
应用模式：深色
```

支持系统主题的应用使用深色；Windows 系统界面保持用户原有设置。

程序只控制 Windows 提供的默认应用模式。应用必须自身支持并设置为“系统默认”或“跟随系统”；网页内容是否变暗仍由网站或浏览器决定。

### 4.4 阶段 1 原型映射

阶段 1 暂以当前用户注册表中的以下字段验证深浅模式：

```text
HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize
├─ AppsUseLightTheme     0=dark, 1=light   # 唯一写入目标
└─ SystemUsesLightTheme  0=dark, 1=light   # 只读不变断言
```

原型必须保留原始类型并执行以下保守策略：

- 字段不存在时记录为 `unset`，不得擅自推断为浅色或深色；
- 显式应用配置时只可以创建或修改 `AppsUseLightTheme`；
- 如果应用失败，而测试前 `AppsUseLightTheme` 不存在，回滚必须重新删除该字段；
- 字段类型不是 `REG_DWORD` 或值不是 `0/1` 时拒绝写入；
- 相同目标应用模式不重复写入，也不广播无必要的刷新消息；
- 每次测试必须确认 `SystemUsesLightTheme` 在操作前后完全相同。

刷新原型使用 `WM_SETTINGCHANGE` 向 `HWND_BROADCAST` 广播，并通过 `SendMessageTimeoutW` 限制无响应窗口造成的等待。微软公开文档支持这一广播方式：[WM_SETTINGCHANGE](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-settingchange)、[SendMessageTimeoutW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessagetimeoutw)。

2026-07-22 在 Windows 11 25H2（build 26200.8875）早期双字段实测时，`lParam = "ImmersiveColorSet"` 的广播调用返回成功，两个注册表字段也读回为浅色，但任务栏、开始菜单和 Windows 设置界面没有变浅。该结果说明不能把消息发送和注册表读回等同于所有 Windows Shell 元素已经刷新；默认 Windows 模式随后退出产品写入范围。

同日早期的 100 毫秒轮询未捕获到手动切换，因而一度得到两个字段始终不存在的结果。随后在 PowerShell 中分别于设置界面选择应用浅色和应用深色后读取同一路径，明确观察到 `SystemUsesLightTheme` 始终为 `0`，`AppsUseLightTheme` 由 `1` 变为 `0`。新的仅应用模式原型又完成 `0→1→0` 实机往返，Windows 设置窗口两次均立即响应，自动备份同时证明系统字段保持 `0`。该结果与微软的 [Windows 设置注册表参考](https://learn.microsoft.com/en-us/windows/apps/develop/settings/settings-common) 一致，并冻结了第一版“只写 `AppsUseLightTheme`”的范围；早期轮询结果仅作为未捕获到变化的历史记录。

## 5. 手动调整规则

用户手动调整主题或强调色的正式入口是：

```text
Windows 设置 → 个性化 → 颜色
```

手动调整保持到下一个固定计划边界。程序不实时监听、不判断修改者，也不提供长期 `manualOverride`。阶段 9 仅在预通知的五分钟决策窗口内建立受 nonce 保护的 `pending-switch` 一次性覆盖，用于跳过或延后当前这一执行点；它不能由普通手动改色自动产生，也不会跨越下一固定边界。

例如：

```text
06:15 自动进入昼间
23:15 用户手动切换为夜间
23:45 自动任务应用夜间配置
次日 06:15 自动进入昼间配置
```

23:45 的写入与用户当前选择相同，不产生反向切换。

为避免破坏尚未到边界的手动调整，产品不设置无条件登录或解锁同步，也不提供手动
“立即同步”。临时调整由 Windows 设置完成，并保持到下一计划边界。

## 6. 自动执行设计

两个计划边界调用同一命令：

```text
ThemeScheduler.exe auto
```

处理流程：

1. 打开单实例执行锁；若已有自动切换正在运行，则记录并安全退出。
2. 加载并校验 `config.json` 和 `state.json`；任一不可信时禁止自动修改 Windows。
3. 若 `paused = true`，不修改主题或强调色，记录后退出。
4. 根据当前本地时间计算目标时段。
5. 若上次结果成功、活动时段可信且将离开该时段，从当前活动主题读取语义强调色并保存给活动时段。
6. 若上次成功活动时段已等于目标，返回 `no-change`；不学习、不写 Windows，以保留固定边界之间的用户手动调整。
7. 复制当前活动主题并保存完整事务备份，在同一个管理副本中只补丁目标应用模式和语义强调色，断言 Windows 模式不变。
8. 通过隔离桥接调用 `IThemeManager2.AddAndSelectTheme`，验证活动主题颜色、应用/Windows 模式和桥接转换；若失败则按调用前主题索引或完整主题回退。
9. 先把自动事务清单推进到 `windows-verified`，再原子更新活动时段、上次运行时间、目标配置和执行结果，最后标记 `state-committed`。
10. 写入日志并完成事务清单；失败时按分级返回稳定退出码，必要时尝试通知。

自动执行必须幂等：同一可信目标时段重复运行直接 `no-change`，不得交换昼夜快照、覆盖用户在本时段内的手动调整或不断改写错误归属。阶段 4 的完整契约见 [AUTO_CORE.md](AUTO_CORE.md)。

### 6.1 休眠、关机与补运行

任务计划设置：

```text
唤醒计算机运行此任务：关闭
错过计划时间后尽快运行：开启
```

补运行不执行“错过的那个固定配置”，而是按启动时的实际时间计算目标。例如设备从前一天 22:00 关机到次日 08:00，恢复后直接应用昼间配置。若 Windows 连续发起多个补运行，结果仍应相同。

### 6.2 状态缺失或损坏

配置或状态缺失、损坏、版本未知，或迁移失败时，自动入口必须：

- 不学习或覆盖任何昼夜强调色配置；
- 不修改应用模式、强调色或 Windows 模式；
- 不用默认状态掩盖损坏证据，也不自动重建 `activeProfile`；
- 返回 `data-untrusted`，尽力记录错误并等待显式修复。

结构合法但 `lastResult` 为 `never`、`failed` 或 `partial` 时可以按当前时间生成目标应用计划，但不得学习当前颜色；中断恢复还必须先满足自动事务清单规则。

### 6.3 退出码和中断恢复

`auto` 的稳定退出码为：成功/无需变化 `0`、暂停 `10`、已有实例 `11`、数据不可信 `20`、应用失败但回滚成功 `30`、部分失败 `40`、未分类致命失败 `50`。Windows 已验证但状态未提交的窗口由版本化自动事务清单覆盖，不能静默当作成功或默认重跑。详细状态转换见 [AUTO_CORE.md](AUTO_CORE.md)。

## 7. 强调色设计

### 7.1 设计原则

阶段 0～10 由 Windows 设置负责选择颜色并生成相关调色板，ThemeScheduler 保存和恢复已经生成的完整结果。阶段 12 的 GUI 可以接受 `#RRGGBB` 或十进制 `R/G/B`，但只据此修改长期语义 `ColorizationColor` 的低 24 位并通过既有管理主题事务应用；它仍不得自行推导或直接写入经典六字段 Windows 调色板。

快照需要支持：

- 昼夜不同颜色；
- 昼夜相同颜色；
- 用户在当前时段通过 Windows 设置修改颜色；
- 离开当前时段时用新颜色覆盖该时段旧记忆；
- 再次进入该时段时恢复其最新快照。

### 7.2 学习与恢复

标准切换顺序：

```text
读取可信的活动时段
→ 捕获当前 Windows 强调色
→ 保存为即将离开时段的快照
→ 从当前完整主题生成复合管理副本
→ 同时补丁目标 AppMode 和目标时段强调色
→ 通过 IThemeManager2 应用
→ 读回验证应用模式、强调色及 Windows 模式不变
→ 更新活动时段
```

示例：昼间蓝色恢复后，用户改为绿色；到夜间边界时绿色保存为昼间快照并恢复夜间红色。夜间用户再改为紫色，次日昼间边界会保存夜间紫色并恢复昼间绿色。

昼夜快照内容相同即可自然实现同色，不需要额外开关。

### 7.3 首次安装

首次安装只有一份当前 Windows 强调色。安装器在修改系统设置前捕获它，并将其复制为昼间和夜间的初始快照。后续切换逐步学习两个时段各自的新颜色。

阶段 2 已冻结：长期配置不保存六个经典颜色注册表字段，而保存 `AutoColorization` 和原始 `ColorizationColor`；每次从当前活动主题动态生成完整管理主题；Shell 应用使用隔离的 `IThemeManager2` 桥接。相关验证记录见 [TESTING.md](TESTING.md)。

2026-07-23 的六字段实机往返表明，`AccentColorMenu`、`AccentPalette`、`StartColorMenu`、`AccentColor`、`ColorizationAfterglow` 和 `ColorizationColor` 只覆盖了一部分强调色消费者：Windows 设置、窗口边框和输入法能够采用写入后的颜色，但任务栏与开始菜单仍可保持旧色。首次正向测试中 Windows 还曾按另一权威状态重新生成原颜色。因此第一版不得把这六项当作足以驱动强调色切换的最终写入接口，也不得把瞬时读回成功等同于完整可见状态恢复成功。

同日只读核对确认当前主题为 `%LOCALAPPDATA%\Microsoft\Windows\Themes\Custom.theme`，其 `[VisualStyles] ColorizationColor=0XC4744DA9` 仍为紫色 `#744DA9`，恰与任务栏和开始菜单的旧色一致。人工操作矩阵进一步确认：只有“在开始菜单和任务栏上显示强调色”已经开启时再从设置页选择颜色，Explorer 才会同步；关闭该开关后选色、再重新开启，只会恢复主题文件中的旧色。这说明阶段 2 的最终应用事务必须同时处理活动主题状态或调用与设置页等价的主题应用入口，不能继续把广播或 `ColorPrevalence` 切换视为充分刷新手段。

原型不得直接覆盖用户的 `Custom.theme`。若验证主题文件路径，应先复制到 ThemeScheduler 管理的文件，最小化修改 `[VisualStyles]` 颜色字段，并保留背景、声音、光标、图标和深浅模式等非目标设置；应用前后都必须保留可人工恢复的原主题引用。

## 8. 暂停与恢复

暂停是必须持久保存的控制状态：

```json
{
  "paused": false
}
```

暂停后计划任务可以继续启动核心程序，但核心程序只记录状态并退出，不修改深浅模式或强调色。

恢复语义已经冻结：恢复只取消暂停，保持当前状态直到下一固定边界，不自动调用主题切换。需要临时改变当前外观时由用户进入 Windows“个性化 → 颜色”，ThemeScheduler 不提供手动立即套用入口。

暂停和恢复只修改 `paused`，保留其余状态字段，也不改变任务启用状态。暂停状态下再次暂停、恢复状态下再次恢复都返回 `no-change`。暂停、恢复和自动任务使用同一个当前会话执行锁；存在未完成自动事务时，控制状态写入必须先保守拒绝。

阶段 6 曾验证独立立即同步实现，但阶段 13 根据产品“计划部署器”定位撤销该正式功能。`AutoRunner.force_apply` 只保留为核心测试与受控诊断能力，不得暴露给产品 GUI、安装器或正式命令路由。完整修订见 [CONTROLS.md](CONTROLS.md)。

## 9. 持久化数据设计

### 9.1 `config.json`

保存用户主动配置和结构版本：

```json
{
  "kind": "themescheduler.config",
  "schemaVersion": 1,
  "schedule": {
    "dayStart": "06:15",
    "nightStart": "23:45"
  },
  "profiles": {
    "day": {
      "appsTheme": "light"
    },
    "night": {
      "appsTheme": "dark"
    }
  },
  "notifications": {
    "errors": true,
    "statusChanges": true
  }
}
```

校验规则至少包括：

- `schemaVersion` 可识别或可迁移；
- 时间采用本地 24 小时制 `HH:mm`；
- 两个时间不相同；
- 主题值只能为支持的枚举；
- v1 精确拒绝未知字段；未来版本只允许显式逐版本迁移，不能静默破坏。

### 9.2 `state.json`

保存运行状态，而非用户首选项：

```json
{
  "kind": "themescheduler.state",
  "schemaVersion": 1,
  "paused": false,
  "activeProfile": null,
  "lastRunAt": null,
  "lastAppliedProfile": null,
  "lastResult": "never"
}
```

`activeProfile` 只用于强调色归属，不用于推断用户行为。时间戳使用带本地 UTC 偏移的 ISO 8601 格式。`never` 是显式安装初始化状态；普通运行中状态缺失或损坏时不得重建为该默认值，而应标记状态不可信并阻止自动系统修改。

### 9.3 强调色快照

长期语义配置分别存放在 `profiles/day.json` 和 `profiles/night.json`，至少包含：

- `kind = "themescheduler.accent-profile"`；
- 结构版本；
- `profile = "day" | "night"`；
- 捕获时间和来源时段；
- `autoColorization`；
- 八位原始 `ColorizationColor`，采用 `0X` 加八位十六进制；
- 捕获时 Windows 构建号。

配置损坏、版本未知或字段非法时不得应用主题，也不得覆盖另一时段的有效配置。六个经典颜色字段可以进入诊断文件，但不得进入正式恢复模型。

当次应用在 `runtime/` 中生成：

- `accent-<时间>-<随机后缀>/before.theme`：完整源主题备份；
- `accent-<时间>-<随机后缀>/managed.theme`：从源主题复制并只补丁目标颜色的管理主题；
- `accent-<时间>-<随机后缀>/journal.json`：源/目标哈希、目标配置、调用前主题索引、阶段和结果。

主题文件写入并刷盘后才能提交引用它们的清单。正常切换完成后可按保留策略清理旧运行文件；失败事务保留用于诊断。

### 9.4 `backup/install.json`

保存安装前真实状态，用于卸载还原；完整主题固定存放为 `backup/install.theme`。v1 清单包括：

- `AppsUseLightTheme`；
- 完整活动主题及其 SHA-256；
- 语义强调色；
- 仅供诊断的经典颜色字段；
- 个性化相关开关；
- 捕获时间、Windows 版本和结构版本。

清单使用 `kind = "themescheduler.install-backup"` 和 `schemaVersion = 1`，并以 SHA-256 绑定 `install.theme`。升级、修复和普通运行不得覆盖首次安装备份；备份损坏时也不得重新生成并冒充原始恢复点，除非用户明确执行“重新建立恢复点”之类的维护操作。

### 9.5 Shell 应用与 Explorer 兜底

正常路径使用隔离进程中的 `IThemeManager2.AddAndSelectTheme`。这是经 Windows 11 25H2 实机往返验证的未公开接口，因此必须：

- 启动时执行只读能力探针并限制到已验证的 Windows 范围；
- 设置桥接超时，桥接崩溃不得带走主进程；
- 使用忽略背景、光标、桌面图标、声音和屏保的应用标志；
- 保存调用前主题索引，失败时通过 `SetCurrentTheme` 回退；
- 不以经典六字段、两个 `ColorPrevalence` 或最终稳定索引作为可见成功判据。

Explorer 重启只作为维护界面的显式故障兜底。计划任务不得静默重启 Explorer。用户触发前必须提示桌面、任务栏和文件资源管理器窗口可能中断；恢复进程必须独立于 Explorer，限定当前用户会话，并在失败时显示通过任务管理器运行 `explorer.exe` 的人工恢复步骤。

阶段 2 收口实现将该动作隔离为 `restart-explorer --confirm-live-explorer-restart`。桥接通过当前会话 Shell 窗口解析唯一 Explorer PID，禁止按进程名批量结束；终止后先为 Windows 自带的 Shell 自动恢复保留等待窗口，只有超时后才从 `%WINDIR%\explorer.exe` 主动启动，避免双重启动额外打开文件资源管理器主页。最终以新 Shell 窗口和新 PID 作为自动成功条件。该命令不属于 `apply-profile` 的自动失败分支，必须由用户在确认可见结果异常后另行触发。

2026-07-23 最终实机验收确认：`IThemeManager2` 主路径完成黄色→紫色→黄色同步往返，窗口边框、任务栏和开始菜单一致且应用/Windows 模式不变；Explorer 兜底在加入自动恢复等待窗口后成功恢复 Shell、保持目标色并且不再额外打开文件资源管理器主页。阶段 2 据此完成，但不自动进入阶段 3。

### 9.6 日志

日志记录：触发时间和原因、目标时段、应用结果、注册表失败、快照保存或恢复失败、配置损坏、状态恢复以及任务计划修复。

日志使用 `logs/events.jsonl`，每行一个 `themescheduler.event` v2 对象，只允许固定
字段，不允许任意 `details`。v2 增加验证、回滚和事务标识字段，并兼容读取 v1。
单文件最大 1 MiB，保留 5 个历史文件。消息最多 500 字符，不得记录不必要的用户
隐私信息、完整环境转储、主题内容或不必要的绝对用户路径。

成功的强调色运行事务保留最近 10 个；失败或不完整事务保留 30 天，并至少保留最近 10 个。详细契约和损坏处理矩阵见 [PERSISTENCE.md](PERSISTENCE.md)。

## 10. GUI 设计

GUI 使用 `pywebview==6.2.1`，加载随程序发布的本地 HTML、CSS 和 JavaScript，Windows 后端固定为 Edge Chromium。GUI 只用于安装、配置和维护，按需启动；关闭窗口后进程退出，不创建托盘或常驻后台进程。

工作 GUI 冻结为单窗口、低密度工作台。左侧活动栏只保留一级功能导航；“计划与外观”内部允许在同一窗口中切换“计划概览”和“设置明细”，但不建立可无限深入的页面层级。默认概览尽量在常见 DPI 下完整呈现，不依赖纵向滚动；维护和调试内容空间不足时允许各自滚动。

阶段 12 曾建立“计划 / 外观 / 维护 / 调试”四页结构；阶段 13 将计划与外观合并，
当前为左侧活动栏中的“计划与外观 / 维护 / 调试”三页。“计划与外观”默认显示只读概览，并由唯一的“设置计划”入口进入独立明细页；普通配置不经过调试页；
`maintenance` 和健康通知激活仍可直接定位维护页并执行一次只读健康检查。

操作 GUI 自身默认跟随 Windows 的默认应用模式，但该行为只控制 ThemeScheduler 窗口的呈现，不代表计划目标，也不得触发应用模式、强调色、任务或 profile 写入。浅色使用 NameToolsSuite 风格的浅蓝灰背景、白色面板、深蓝标题和亮蓝选中态；深色使用 Dracula 核心色板。左侧活动栏底部的单一主题按钮只在当前窗口内临时反转系统主题；按钮始终以太阳或月亮表达当前浅色/深色界面，覆盖状态及恢复跟随 Windows 的动作只写入悬浮说明，不用返回图标替代当前状态。覆盖后再次点击恢复自动跟随，关闭窗口即丢弃覆盖，不写配置或 Web 存储。Windows 在窗口存续期间改变默认应用模式时，未覆盖状态必须即时响应。

工作 GUI 使用随 `ui/fonts/` 交付的 Source Han Sans SC 2.005 界面字符子集，CSS 字体族使用项目专用名称，避免依赖目标机器字体注册。每次增加界面文案后必须由锁定的 FontTools 重新扫描 `ui/` 生成子集，并更新字体资源版本以避开 WebView2 旧缓存。子集及 SIL OFL 许可进入正式载荷，完整字体不进入载荷；Noto CJK、微软雅黑和 Segoe UI 继续作为资源异常时的回退。

前端通过最小白名单 API 调用既有业务用例。API 只接受结构化输入并返回结构化
结果；Python 侧以 TypedDict 定义线协议，JavaScript 在响应进入页面状态前校验
公共信封和关键嵌套字段。API 不直接暴露文件系统、注册表、PowerShell 或任意命令
执行；前端不得复制时段判断、主题写入、任务计划或持久化逻辑。正式构建关闭调试
模式，不加载远程页面。WebView2 用户数据固定到
`%LOCALAPPDATA%\ThemeScheduler\WebView2`。

### 10.1 安装界面

安装界面包含：

- 固定且只读的当前用户安装目录；
- 是否创建桌面快捷方式；
- 安装、取消和完成页启动主 GUI按钮。

时间、应用模式、强调色和立即同步不在安装器中配置。首次安装完成后由主 GUI
统一呈现两套配置；在用户第一次成功保存前，自动切换保持暂停。Setup 检测到
同版本可信安装时自动切换为“修复 / 重装”说明，完整替换程序文件并修复系统集成，
同时保持可信用户数据和当前外观。

### 10.2 配置与维护界面

配置程序提供：

- 修改两个时间和昼夜应用模式；
- 修改昼夜强调色，并实时预览 HEX/RGB 草稿；
- 查看当前计算时段、活动时段和快照是否存在；
- 暂停与恢复；
- 打开 Windows 颜色设置；
- 查看日志和打开配置目录；
- 检查或修复任务计划；
- 启动卸载程序。

“计划与外观”的默认主页采用大计划概览与窄操作列：计划区域按纵向层级呈现 24 小时总览、昼间和夜间的时间/应用模式/颜色；操作列突出“设置计划”，并显示实际 Windows 外观、自动切换开关及“恢复安装前外观”。旧的四格运行摘要不再占用首屏。保存设置成功后返回概览并重新读取状态；从有未保存草稿的设置页返回时必须确认放弃。

设置明细页保持“左侧共享表盘、右侧当前时段字段”的单层布局。昼间和夜间使用标签切换；分别拖动一次时针与分针后自动切到另一时段，并以窗口中央的短时淡入提示确认。昼间表盘使用浅底深针，夜间表盘使用深底浅针，切换时以淡入淡出过渡；选中指针使用明显光晕。上午/下午与应用浅色/深色均使用整块可点击的动画二态滑块，不再提供重复的“切换半天”按钮。保存或验证产生的“配置与任务”结果仅在有结果时显示于右侧颜色区下方，底部只保留草稿状态和保存动作。

从控制面板“更改”启动时，统一入口使用 `maintenance` 参数打开同一窗口的维护区，不建立第二套 GUI。维护区提供：

- 恢复默认时间和通知设置；
- 检查/修复任务并打开日志、数据目录；
- 启动独立卸载器。

恢复安装前外观不是程序文件修复。操作前必须取得自动核心同一互斥、拒绝未完成事务、严格验证首次安装备份并先提交 `paused=true`；随后从当前活动主题生成管理副本，只应用备份中的 `AppMode` 和语义强调色，保持当前 `SystemMode`、壁纸和其他非所有字段。恢复失败也保持暂停，避免后续边界覆盖用户正在处理的外观。

“重置默认时间和通知”只把边界恢复为 `06:15`/`23:45`，并重新启用错误通知和状态变化通知；它保留用户当前选择的昼夜应用模式及两份语义强调色记录。该操作通过配置—任务同一事务修复单任务 v2 定义，不重建安装前外观恢复点。

概览操作列必须独立显示首次安装恢复点的状态。仅当 `install.json`、`install.theme`、主题哈希、应用模式及原始 `AppsUseLightTheme` 语义全部一致时，才允许恢复；缺失、不完整或损坏只报告“不可可信恢复”，不得以当前外观伪造新的原始恢复点。维护区启动独立卸载器与概览恢复外观使用不同的确认动作。

保存配置的流程是：

```text
校验输入
→ 原子写入 config.json
→ 更新任务计划时间
→ 读回验证任务计划
→ 显示成功、失败或不一致状态
```

可提供配置导入、导出、恢复默认值和使用默认编辑器打开 JSON 的高级入口，但普通用户不需要手动编辑 JSON。

### 10.3 时间轮盘

“计划”页同时包含一个可编辑的 12 小时表盘和一个只读的 24 小时计划总览。两者使用同一份尚未保存的页面草稿，但职责不同：

- 12 小时表盘负责直接设置数字；
- 24 小时表盘负责准确展示整日分布；
- 核心层仍只接收规范 `HH:mm`，前端不得复制时段归属判断。

#### 10.3.1 12 小时交互表盘

编辑器右侧以互斥且高亮的“昼间 / 夜间”标签明确当前边界，点击标签或使用标签键盘导航可切换，切换时保留两个边界的草稿。表盘使用短粗时针和长细分针；表盘下方以 24 小时制 `HH:mm` 显示当前草稿。选中时针时高亮小时部分，选中分针时高亮分钟部分。

交互规则冻结为：

- 分针吸附到 5 分钟刻度，只改变分钟，不移动时针，也不改变上午/下午；
- 时针只改变小时并保留分钟；显示时始终指向选中的整点数字，不按分钟产生机械式偏移；
- 时针拖动必须累计角度，顺/逆时针跨越半天边界时更新上午/下午；从任意位置完整周转一圈等价于 `±12` 小时；
- 另提供显式上午/下午控件和一个“切换半天（±12 小时）”操作；在 24 小时值上加减 12 小时结果相同，因此不重复提供正负两个按钮，用户也不必依赖完整周转；
- `HH:mm` 文本输入与表盘双向同步，并按同一 5 分钟步进校验；
- 键盘选择时针或分针后，方向键分别按 1 小时或 5 分钟调整；焦点、当前编辑边界和当前选中指针不得只靠颜色表达。
- 在同一边界编辑会话中，时针和分针各完成一次实际改变数值的拖动后，自动切到另一个边界；单击指针、键盘调整、直接输入时间、上午/下午或 `±12` 小时操作均不触发该自动切换。用户手动选择边界时重新开始统计。

表盘配色跟随当前编辑边界而非 GUI 明暗主题：昼间使用近白表盘和近黑指针，夜间使用近黑表盘和白色指针；选中状态通过中心针、光晕、数字高亮及文字共同表达。

分针拖动是高频操作，因此即使连续转过一圈或多圈，也只能更新 `minute mod 60`，不能隐式增加或减少小时。时针拖动则按累计小时变化计算 24 小时值，例如从 `11:xx` 顺时针越过 12 到 `01:xx` 会跨越上午/下午，从 `06:xx` 完整顺转回到 6 则增加 12 小时。

#### 10.3.2 24 小时只读总览

总览的一整圈表示 `00:00–24:00`，不显示当前系统时间、秒针或可拖动控件。昼间和夜间边界各使用一根单指针；两根指针长度不同，端点形状不同，以便重合或近重合时仍能共存。

指针角度按完整分钟连续计算：

```text
minuteOfDay = hour × 60 + minute
angle = minuteOfDay ÷ 1440 × 360°
```

因此 `06:25` 位于 6—7 区间的约 `41.7%`，`07:45` 位于 7—8 区间的 `75%`。表盘固定以正上方 `0`、右侧 `6`、下方 `12`、左侧 `18` 强化 24 小时方向；每小时保留主刻度，每小时之间只绘制四节辅助刻度，但不把指针近似或吸附到 15 分钟。

总览包含两个有方向的环段：

- 从昼间边界顺时针到夜间边界为浅灰昼间环段；
- 从夜间边界顺时针跨午夜回到昼间边界为深蓝夜间环段。

悬浮环段显示模式名称、准确起止时间和持续时长；悬浮指针端点显示对应边界与准确时间。文字图例、不同长度和不同端点形状共同承担区分职责，颜色不是唯一信息来源。两个边界相同属于不可保存的草稿错误；总览仍以重合指针和零/整圈边界状态确定显示，不擅自改变用户时间。

### 10.4 阶段 12 页面草稿与提交

工作 GUI 读取可信 `config.json`、昼夜 profile 和只读状态后建立页面草稿。标签页切换、时间或颜色数字编辑和模式选择只修改草稿，不产生任务、主题或配置写入。

颜色编辑同时呈现 Windows 设置中常见的两种等价表示：

```text
#FFB900
R = 255
G = 185
B = 0
```

十六进制与三个十进制字段必须实时双向同步，任一字段非法时只显示内联错误并保持最后一个有效草稿。十六进制控件把 `#` 固定为不可编辑前缀，用户只需输入六位 `RRGGBB`；粘贴完整 `#RRGGBB` 时应自动规范化，而不是要求再次删除前缀。profile 的持久值仍是原始 `0XAARRGGBB`：界面读取低 24 位还原 `#RRGGBB` 和十进制 RGB，并单独保留高 8 位 `AA` 语义字节；用户修改颜色时只替换低 24 位。例如 `0XC4FFB900` 可无损显示为 `#FFB900` 和 `RGB(255,185,0)`，保存后仍为 `0XC4FFB900`。若已有有效 profile 使用其他 `AA`，必须保留该原值而不能统一覆盖为 `C4`。profile 缺失、损坏或版本未知时拒绝保存，不以默认高字节伪造新 profile。

外观页不提供图形选择盘、原生拾色按钮、快捷色板、最近颜色、昼夜颜色复制或互换。每个时段只提供十六进制、十进制 RGB 和一个醒目的已选颜色预览；预览必须明确标注为配置草稿，尚未应用到 Windows。

每个时段另提供“导入当前外观”辅助入口。它只读取活动 `.theme` 中的应用模式、系统模式、自动取色状态和 `ColorizationColor`，把当前应用模式及可见 RGB 写入所选时段的页面草稿；不得写 profile、config、任务、注册表或主题，也不得自动触发保存。系统模式只用于返回和诊断，不导入到产品配置。隔离安全预览不访问真实 Windows 主题，因此该按钮必须禁用；正式安装态才开放。

提交只有一个正式动作：

- **保存**：以一个受锁和可回滚的组合事务提交 `config.json`、`profiles/day.json`、`profiles/night.json`，并按既有配置—任务事务更新和读回任务定义；不改变 Windows 外观。首次设置时显示为“保存并启用”，同时清除首次设置标记并解除暂停，仍不立即套用主题。

任一输入损坏、结构版本未知、原 profile 不可信或组合保存无法完整回滚时，都不得用默认值覆盖已有数据。

GUI 模块必须延迟导入。任务计划调用 `ThemeScheduler.exe auto` 时不初始化 pywebview、WebView2 或前端资源，也不因此增加可见窗口。

源码阶段使用显式 `--data-root` 启动安全预览。安全预览允许只读概况、输入校验、开发数据根内的暂停/恢复和打开固定系统入口，但后端阻止保存配置所隐含的任务更新及任务修复。只有另行启用实机写入并提供明确可执行文件目标后，这些按钮才可在二次确认后产生副作用；Python 解释器不得作为正式任务目标。

## 11. 任务计划设计

第一版采用一个任务。阶段 9 的 v2 定义包含四个固定每日触发器，并在延后本次切换时临时增加一对一次性触发器：

```text
\ThemeScheduler
├─ DayPrepare         <dayStart-5min>
├─ DayBoundary        <dayStart>
├─ NightPrepare       <nightStart-5min>
├─ NightBoundary      <nightStart>
├─ DeferredPrepare    <deferredAt-5min>  # 可选
└─ DeferredBoundary   <deferredAt>       # 可选
```

计划必须满足：

- 四个固定触发器和可选延后触发对均调用 `ThemeScheduler.exe auto`；
- 使用当前用户上下文和正式安装目录的绝对路径；
- 不唤醒计算机；
- 错过计划后尽快运行；
- 使用交互式用户令牌和最低权限，只在该用户登录时运行；
- 使用 `IgnoreNew` 多实例策略，允许电池供电运行，不依赖网络；
- 不添加登录、解锁、系统恢复或周期轮询触发器；
- 支持创建、更新时间、检查、禁用和删除；
- 延后触发器只能成对出现，必须与可信 `pending-switch` 状态一致，消费或过期后整体删除；
- 更新后可读回触发器、命令、参数和路径进行验证。

各触发器只保留稳定诊断 ID，不把昼夜配置或动作硬编码进不同命令。任务历史只能说明进程是否启动；实际处于预提醒窗口、边界执行还是错过补运行，均由应用按当前时间和可信状态判断。

任务更新通过一次完整定义注册替换全部触发器，随后读取规范化定义并逐字段比较。注册或读回失败时恢复旧完整定义；原任务不存在时删除可能留下的部分定义。GUI 的配置保存通过 `ConfigurationService` 执行：与自动运行共享互斥锁，拒绝未完成自动事务；在写入前完成输入和期望任务校验，配置与任务分别读回。任务协调失败时恢复旧配置，已有任务由任务组件使用完整 XML 备份恢复；任一恢复无法验证时返回部分失败并要求修复。进程中断则由 `check/repair` 以有效配置和可信一次性覆盖状态为期望源收敛。详细字段和验收矩阵见 [SCHEDULER.md](SCHEDULER.md)。

正式 `ThemeScheduler.exe` 使用无控制台的 Windows GUI 子系统构建。任务仍保持 `Hidden=false` 以便用户检查，但 `auto` 正常运行不得弹出 CMD/PowerShell 窗口。阶段 5 的控制台构建曾在手动启动任务时产生可见窗口；改用无控制台构建后，连续两次任务启动均无窗口，其中一次由用户现场观察确认，同时未改变强调色或应用模式。

主程序无控制台并不能自动隐藏其子进程。任务计划、`IThemeManager2` 主题应用和 Explorer 维护兜底调用 PowerShell 时，必须统一传入 `CREATE_NO_WINDOW` 与隐藏 `STARTUPINFO`。阶段 7 首轮 GUI 实机验收曾在首次概况加载和控件调用时观察到瞬时 CMD；加入共享无窗口策略后，GUI 启动、任务检查和立即同步均由用户复验无闪窗。

## 12. 安装、升级与卸载

### 12.1 首次安装

安装器按以下顺序执行：

1. 使用原生 Windows 界面校验系统支持范围、WebView2 Runtime 和目标目录。
2. WebView2 缺失时，经用户知情并验证 Microsoft Authenticode 签名后运行随安装器提供的 Evergreen Bootstrapper；离线包可提供 Standalone Installer。失败则停止，不降级到 MSHTML。
3. 在首次修改前捕获安装前个性化设置并安全保存。
4. 把正式 `onedir` 主程序和独立卸载器解包到 `.staging-<事务>`，按载荷清单逐文件验证后切换到正式路径。
5. 创建初始配置、状态和两份强调色快照。
6. 创建任务计划及开始菜单快捷方式，可选桌面快捷方式。
7. 注册当前用户“已安装的应用”条目；“更改”指向主程序维护区，“卸载”指向独立卸载器。
8. 运行文件、配置、任务和 Windows 访问自检。
9. 完成页允许打开主 GUI；Setup 本身不立即同步 Windows 外观。

任一步失败都要记录已完成步骤，并按事务策略回滚或保留为可修复状态，不得显示模糊的“安装成功”。

Setup 界面只接受是否创建桌面快捷方式这一项可变安装选择；安装位置固定显示为当前用户程序根，不允许前端提交任意路径。昼夜时间、两种应用模式、两份强调色和立即同步都不属于安装器选项，开始菜单快捷方式始终创建。

经典 Setup 使用约 `720 × 540` 的固定单窗口向导，左侧为品牌和纵向步骤，右侧依次呈现欢迎、安装选项、确认、真实进度及完成/失败页，底部导航位置固定。浅色和 Dracula 深色自动跟随 Windows，不在安装器内提供手动主题按钮。首次安装不编辑产品配置：安全默认配置只用于建立完整数据结构，状态以首次设置暂停态初始化；主 GUI 显示首次设置提示，并暂时隐藏尚不可用的暂停和恢复控制。第一次“保存并启用”只解除暂停，不自动改变 Windows。重装和升级明确说明配置、状态、昼夜颜色、日志和首次恢复点原样保留。

“下一步”只导航并执行无副作用校验，只有确认页的“安装”才启动事务。进度页必须显示安装核心报告的真实粗粒度阶段，不按计时器伪造百分比。安装或回滚运行期间，底部取消、完成按钮和窗口右上角关闭均被阻止；事务结束后才允许退出。失败页在当前窗口内显示失败阶段、回滚结果、事务编号和固定日志入口，正常流程不叠加消息框。

“保留数据”只指 `config.json`、`state.json`、两份颜色配置及首次安装恢复点这组六项核心数据。六项全部不存在时，Setup 使用安全默认值初始化，写入 `paused=true` 和独立、严格验证的 `initial-setup.json` 临时标记；仅有旧日志或 WebView2 缓存不妨碍初始化，且这些旧内容继续保留。六项全部存在时必须逐项严格验证并原样保留，安装界面选项不覆盖它们；只存在一部分或任一项损坏时停止并提示修复，不自动补齐。

当前用户系统集成以一个事务协调三类对象：固定的开始菜单快捷方式、可选桌面快捷方式，HKCU `Uninstall\ThemeScheduler` 登记，以及 `\ThemeScheduler` 单任务 v2 定义。写入顺序为快捷方式→登记→任务，失败恢复按任务→登记→快捷方式逆序执行。快捷方式只允许无参数启动已安装的 `ThemeScheduler.exe`；登记精确读回“更改/卸载”命令；任务沿用完整 XML 备份，不能用规范化字段替代原定义。

实机验收或安装协调器开始修改前，还要持久化独立恢复快照：登记键的全部值和原类型、两个 `.lnk` 的原始字节/不存在状态、任务规范模型及完整 XML。应用前若当前状态与快照不一致则停止，避免用过期快照覆盖用户或其他进程刚做的更改。

### 12.2 升级

升级应保留配置、昼夜快照、必要状态和首次安装备份；迁移旧结构，更新程序文件、独立卸载器、安装登记与任务计划并运行自检。用户也可在不预先清理损坏文件的情况下运行同版本 Setup 重装。

升级和重装不得直接覆盖旧 `app`。新载荷先在 `.staging-<事务>` 中完成路径、大小和 SHA-256 验证；取得生命周期与自动互斥、关闭 GUI 后，把旧组件移入 `.rollback-<事务>`，再切换新组件。活动载荷验证后进入延迟完成的 `committed` 状态，旧树继续保留；登记、快捷方式、任务和最终自检全部成功后才清理旧目录。后置失败先恢复系统集成，再恢复旧程序树，并只删除本次安装新建的数据。若任一恢复无法验证，报告 `partial` 并保留证据，不得启用不可信入口。

Setup 不执行安装后立即同步。首次新建数据时，任务可以完成登记，但自动入口同时受 `paused=true` 和首次设置标记阻止，普通“恢复”也不能绕过该标记；用户在主 GUI 第一次成功保存计划与昼夜外观后解除暂停并删除标记，仍保持当前 Windows 外观，等待下一计划边界。同版本重装、升级以及复用保留数据的再次安装均保持原有暂停状态，不重新触发首次设置。

Setup 启动预检在显示第一页前分类操作：无可信程序记录为安装，同版本为“修复 / 重装”，旧版本为升级，新于载荷的版本拒绝降级。同版本路径使用与阶段 8.6 相同的暂存、逐文件校验、目录交换和失败回滚，即使主 EXE 损坏也不依赖它完成修复。结果页成功时提供“完成并打开 ThemeScheduler”和“退出”；失败结果只能关闭或查看日志，不能启动未验证程序。

### 12.3 卸载

推荐顺序：

```text
把独立卸载器复制到严格限定的临时目录并启动
→ 禁用任务
→ 停止正在运行的任务
→ 删除任务
→ 按用户选择恢复接管前的应用模式和强调色
→ 删除快捷方式和当前用户安装登记
→ 删除整个独占程序根，包括损坏文件、桥接脚本和安装元数据
→ 按用户选择删除或保留配置、快照和日志
→ 以固定无窗口清理脚本删除临时卸载工作区
```

卸载界面提供：

```text
○ 恢复 ThemeScheduler 接管前的应用模式和强调色
○ 保持当前应用模式和强调色

□ 保留配置和昼夜颜色记录，供以后重新安装
□ 保留日志
```

经典卸载界面复用生命周期共享向导，采用约 `720 × 540` 固定单窗口，依次显示
欢迎、三个选项、自然语言确认、真实阶段进度和完成/部分失败。三个选项必须位于
同一页；确认、成功和可预期错误不得通过连续原生消息框完成。安装目录中的
`Uninstall.exe` 在确认后只生成严格授权请求并启动已验证的临时副本，然后关闭
原窗口；临时副本用同一套 GUI继续显示实际进度与结果。这个短暂的进程交接用于
释放安装目录内的可执行文件锁，不改变用户所见的单向导流程。

卸载前端只能调用读取状态、校验选项、启动唯一后台卸载会话、轮询状态和受控关闭
这组白名单 API。后台事务期间，页面按钮、关闭 API 与窗口 `X` 使用同一禁止关闭
状态；只有事务已完成或已形成可重试的部分失败结果后才能退出。成功页明确说明
临时工作区会在窗口退出后由固定无窗口脚本清理；部分失败必须显示残留数量和重试
方向，不能声称完整卸载。

`runtime/` 和 `WebView2/` 属于运行缓存，卸载时始终删除。首次安装备份恢复成功后删除；未恢复时只随“保留配置和昼夜颜色”选项保留。主程序、`_internal` 或其桥接脚本损坏不能阻止卸载器删除任务和程序，因为 `Uninstall.exe` 必须自包含最小运行库和卸载桥接，不从主 `onedir` 导入。

若任务删除、程序根删除或临时自删除失败，必须显示具体残留并提供重试或重启后清理，不能报告完整卸载。完整布局、登记、清理矩阵和事务状态见 [INSTALLATION.md](INSTALLATION.md)。

## 13. 通知与错误处理

关闭状态变化通知时正常计划切换保持静默。启用时，每个固定或延迟执行点提前 5 分钟显示预通知，提供“跳过本次 / 延迟 30 分钟 / 确认”；无操作和确认均按原时间执行。实际切换并验证成功后等待 5 秒再显示成功通知。

错误通知正文可以点击，但只绑定唯一固定入口 `themescheduler-action://health/`。点击后打开或聚焦现有 ThemeScheduler 单窗口，定位维护区并自动运行一次只读健康检查；报告以中文区分“正常”“警告”“需要修复”“需要处理”，并自动滚动到可见位置。URI 不接受参数、文件路径或命令，点击本身不执行修复。任务修复和通知身份修复仍须分别点击维护区按钮并确认。成功通知保持不可交互；预通知的三个按钮继续使用受 nonce 保护的切换动作 URI。

- 配置或状态损坏；
- 注册表应用或读回验证失败；
- 任务计划异常；
- 暂停、恢复或自动修复结果。

通知实现需验证 AppUserModelID、开始菜单快捷方式关联和后台触发稳定性。通知失败不得影响核心切换结果，必须退化为日志记录。

阶段 9 开工基线进一步约束：

- 无变化、另一实例运行和暂停期间计划触发保持静默；
- `notifications.errors` 只控制异常通知；`notifications.statusChanges` 控制用户主动暂停/恢复、显式修复，以及固定/延后切换的预通知和成功通知；
- 通知位于核心事务确定结果和退出码之后，失败只追加 `notification.delivery-failed`，不得触发主题、状态、任务或配置回滚；
- 健康检查使用 `healthy`、`warning`、`repairable`、`action-required` 四级结果，检查本身不自动修复；
- 首版只允许显式修复任务定义和产品快捷方式通知身份；不可信数据和程序文件继续要求用户处理或运行 Setup。
- 错误通知点击只负责导航和只读检查；不得把通知激活等同于用户对修复或系统写入的确认。

延迟会在同一根任务中建立新的“一次性预通知＋一次性执行”触发对：原执行点 `T` 被延迟后，在 `T+25min` 重新提示、`T+30min` 执行。新的预通知到点时生成新 nonce，仍提供相同按钮；再次延迟继续整体后移 30 分钟，但不能跨过下一固定昼夜边界。上一轮 nonce 在延迟动作提交时立即失效。按钮通过一次性 nonce、计划时间、目标时段和过期时间绑定的产品 URI 协议处理，不允许 URI 直接写主题。

候选 AppUserModelID、占位 Toast CLSID、协议安全、检查矩阵和实机门槛见 [NOTIFICATIONS_AND_HEALTH.md](NOTIFICATIONS_AND_HEALTH.md)。

错误处理遵循以下原则：

- 输入和持久化数据在产生副作用前校验；
- 多步操作记录阶段和结果；
- 无法确认颜色来源时宁可不学习，也不污染快照；
- 部分成功必须向 GUI 和日志明确呈现；
- 核心命令用退出码区分成功、暂停、可恢复错误和失败。

## 14. Windows 夜间模式联动

Windows 色温“夜间模式”与应用深浅主题是不同功能。ThemeScheduler 第一版明确不检测、不配置也不联动该功能。用户如需色温计划，应继续在 Windows 设置中独立管理，例如：

```text
23:45 开启
06:15 关闭
```

ThemeScheduler 只负责默认应用模式和强调色，且保持默认 Windows 模式不变。GUI 与安装器不展示夜间模式状态，不比较其时间，也不依赖未公开、易变化的内部接口。

## 15. 安全与发布约束

- 不关闭或绕过 Defender、SmartScreen。
- 不自动创建 Defender 排除项。
- 不使用 UPX、代码混淆、Base64 隐藏命令或动态下载并执行应用代码；经用户确认和签名验证的微软 WebView2 Evergreen 系统依赖安装除外。
- 不使用不必要的管理员权限，不写入 Windows 系统目录。
- 只修改当前用户范围设置。
- 使用稳定的程序名称、图标、版本和发布者元数据。
- 发布 SHA-256 并保留源码和可复现构建过程。
- 使用项目专用 `uv` 环境和 `uv.lock` 锁定发布输入，不依赖全局包。
- 正式主程序采用 PyInstaller `onedir`；单文件只用于 GUI 安装器和独立卸载器。
- pywebview 只加载本地资源，固定使用 Edge Chromium，不静默降级到旧渲染器。

首版 ThemeScheduler 自有可执行文件不采用 Authenticode 签名，适用场景限定为向少量熟人分发。安装器必须明确说明未经签名的新可执行文件可能触发 SmartScreen，并随发布物提供 SHA-256、载荷清单、固定版本/发布者元数据和可复现构建记录；不得通过降低系统安全级别处理误报。这里不改变 WebView2 依赖的信任要求：随包运行的 Microsoft Evergreen 安装程序仍必须验证其 Microsoft Authenticode 签名。

正式候选还必须把 release 全量测试报告绑定到同一源码身份，不能使用旧报告为后续修改背书。无 Git 仓库时，源码身份由受控项目文件的规范路径、大小和逐文件 SHA-256 计算；候选记录同时保存 Python、uv、PyInstaller、pywebview、Windows 构建、`uv.lock`、载荷清单和三个 EXE 的哈希及 PE 属性。详细门槛见 [RELEASE.md](RELEASE.md)。
